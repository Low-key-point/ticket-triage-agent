# 银行客服工单分流与人工复核 Agent 需求分析

版本：1.0

日期：2026年11月6日

课程：机器学习

项目阶段：需求分析与验收设计

## 1 项目定位与选题依据

本项目面向处理在线银行业务咨询的一线客服，设计一个将用户诉求整理为可处理工单的 Agent。系统接收一段英文咨询文本，通过机器学习识别业务意图，查询本地业务分类和处理说明，给出建议队列；对低置信度、范围外、多意图或敏感请求，转入人工复核，并记录处理依据。界面与项目文档使用中文。

选题对应课程材料中的“新闻、评论或工单分类”模块，重点落实文本特征、朴素贝叶斯、线性分类模型和模型评估。选择该方向，是因为有公开的细粒度意图分类数据，普通 CPU 即可开展对照实验，也容易将分类错误与实际分流失败联系起来。项目价值由正确分流、减少重复判断和保留人工控制体现，而非依赖通用聊天能力。

本文件规定后续原型需要实现和验证的能力。模型分数、任务完成率和节省时间均为拟验证指标，不代表已经取得的实验结果。

## 2 用户需求与业务场景

### 2.1 目标用户

主要用户是一线客服或课程演示中的模拟客服，负责阅读咨询、确认分类和修正建议。次要用户是维护分类规则的项目开发者，负责更新模型、标签映射和知识条目。课程评阅者需要能够复现数据处理、训练和评估过程。

### 2.2 待验证的需求假设

在在线客服场景中，同一业务可有多种表达，卡片未送达、卡片失效、转账取消等相近诉求需要分给不同处理队列。人工分流可能产生重复阅读和误判；简单关键词规则可能无法处理同义表达、否定句和拼写错误。公开数据集能够支持意图识别问题的研究，但不能直接证明某家机构存在特定程度的效率损失。[1][2]

因此，开发前拟邀请3—5名具有在线客服使用经验的同学参与模拟任务访谈，了解哪些信息最有助于判断，记录完成步骤及常见分歧。受访者不是银行专业客服时，应如实记录背景，不将结果推广到实际银行生产环境。若无法开展访谈，需求价值主要以公开任务定义和模拟对照实验说明，并保留这一限制。

### 2.3 核心场景

用户输入“I made a mistake and need to cancel a transaction”。系统输出候选意图、校准后的概率估计、建议队列和相关处理说明。符合自动分流条件时，生成本地工单；条件不足时，进入复核队列。客服可确认或改正意图，系统保存最终决定及原因。此处文本是来源仓库列出的任务示例，示例中的系统响应只是目标行为，不是实测预测。[1]

一次任务成功，应满足输入被正确处理、最终状态明确、分流符合标注或复核政策、工具结果可追溯。只显示分类标签不算完整业务闭环。

## 3 项目目标与范围

第一阶段完成可离线演示的单机原型，包括文本输入、77类意图预测、候选队列、处理说明检索、人工复核、处理记录及评估导出。使用 BANKING77 的英文文本；中文界面并不代表模型支持中文理解。

业务队列属于本项目设计的演示规则。需要为全部77个标签建立版本化映射，例如卡片物流、卡片使用、转账、现金与充值、账户资料及其他业务。队列划分不得描述为某家银行的真实组织结构；标签到队列的映射须逐项复核，避免仅凭命名自动归类。

本阶段不接入真实银行账户，不执行支付、退款、挂失或账户修改，不采集真实客户身份信息，不承诺提供官方业务答复。自动操作仅指在本地原型中创建和分配模拟工单。中文识别、语音输入、云端部署及大模型摘要列为后续扩展，不影响核心原型的验收。

## 4 输入输出与使用流程

### 4.1 输入要求

单条文本为必填，去除首尾空白后长度应在5—2000字符之间。批量输入使用 UTF-8 CSV，包含唯一的 ticket_id 和 text 两列，一次最多500条。系统应提示空文本、重复编号、字段缺失、超长文本和不支持的文件编码。无法支持的语言进入明确的非英文或语言不确定状态，不把语言检测结果视为绝对可靠。

### 4.2 输出要求

每条结果包含工单编号、原文的脱敏预览、前三个候选意图及概率估计、建议队列、处理说明编号及版本、是否需要人工复核、触发原因、最终状态和各阶段耗时。置信度表示经验证集校准的模型估计，不表示业务正确性的保证。

分类说明应展示支持预测的主要文本特征或相似训练样例，并清楚标记为模型依据；说明不能证明用户真实身份，也不能当作权威银行政策。知识条目由项目自编并标记为演示内容，提供适用意图、需要补充的信息和人工接管条件。

### 4.3 Agent 状态与动作

```text
接收请求 → 校验与脱敏 → 意图分类 → 分流政策判断
                                  ├─ 符合条件 → 查询处理说明 → 创建模拟工单 → 完成
                                  └─ 需要复核 → 展示候选与原因 → 人工确认或修正 → 完成
工具失败 → 有限重试 → 仍失败则保留现场并进入人工复核
```

状态至少包含 received、validated、classified、needs_review、routed、closed 和 failed。空输入等问题直接返回校验错误，不创建正常工单。复核任务在人工决定前保持待处理状态；不得将“成功进入复核队列”一律统计为“任务已解决”。

Agent 通过状态和策略选择分类、查询、保存、等待人工等动作，使用有界工作流控制执行顺序，无需额外大模型 API。工具输出在进入后续步骤前进行结构校验；相同请求重复提交应复用既有工单或返回重复提示，避免重复创建。

## 6 数据需求与划分

### 6.1 数据来源

使用 PolyAI 发布的 BANKING77 数据，官方仓库列出训练集10,003条、测试集3,080条、77个意图，仓库数据采用 CC BY 4.0 许可。[1][3] 本次核对的上游提交为 `57ec275d8078af65b7731c2a98be812d844a6d6b`。实现时应固定该提交或明确记录替代提交，并保存下载文件的 SHA-256。

这些数据是已标注的银行咨询语句，并不包含真实客服的队列分配、处理时长或解决结果。因此，77类识别的结论可来自公开测试集；队列效率、任务闭环和人工耗时必须另行通过本项目制定的映射、模拟任务和人工实验验证。

### 6.2 训练与测试隔离

保留官方3,080条测试样本作为最终测试集。官方训练集按标签分层，原则上划分为70%训练、15%概率校准、15%策略验证，随机种子固定为42，实际条数以划分清单为准。模型和特征选择在训练部分内使用3折交叉验证；校准集用于概率校准；策略验证集用于选择复核阈值和规则。最终测试集不得参与上述选择。[5][6]

训练前核查空值、非法标签、类别数量和重复文本。完全重复或高相似的改写样例按组隔离，避免跨内部划分泄漏；若与官方测试集存在重合，训练侧移除重合项并记录数量，测试侧保留官方样本并单独报告影响。训练集清理后的实际数量和每类支持数必须随实验记录发布。词表、IDF及其他学习型预处理只能在相应训练折内拟合。

### 6.3 边界与流程数据

额外编写120条边界测试，分为范围外咨询、非英文输入、缺失或异常输入、多意图、敏感请求、工具故障六组，每组20条。每条包含预期动作和判定理由，经人工复核后冻结；另建独立开发样例供规则调试。此类数据明确标记为人工构造，不与公开真实咨询测试集混算主指标。

另从未用于训练和调参的公开测试样本中，按固定规则抽取60条构成模拟客服任务，尽量覆盖多种意图和易混淆情形，并标注其作为原测试集子集的关系，不宣称为新增独立数据。规则约定的最终队列由两人独立核对，分歧交由讨论解决；个人项目无法获得双人标注时需记录限制。

## 7 机器学习方法需求

文本处理保留否定词和有辨别力的词组，比较词级 TF-IDF 与补充字符 n-gram 的效果。所有清洗、向量化和模型步骤放入统一 Pipeline，确保训练和推理处理一致。[4]

设置三类基线：多数类作为最低参照；固定关键词规则体现简单流程；TF-IDF 加多项式朴素贝叶斯体现课程基础方法。主要候选模型为 TF-IDF 加逻辑回归，以及 TF-IDF 加线性 SVM。词级 n-gram 比较1—1与1—2，字符特征作为可选消融，正则化参数在预先列出的有限网格内选择，避免无边界搜索。

线性 SVM 的 decision_function 是间隔分数，不能直接当作概率。使用独立校准集进行 sigmoid 校准，必要时检查逻辑回归的可靠性图与校准误差。选择最终模型时同时考察宏平均 F1、各类召回率、置信度可靠性和推理耗时，不只追求单项最高准确率。[5]

自动分流须同时满足最高类别概率不低于阈值 τ、前两候选概率差不低于 δ、不存在敏感或范围外触发条件、队列映射与知识查询成功。τ 和 δ 由策略验证集确定；阈值冻结后再运行最终测试。若验证集无法兼顾自动分流精度与覆盖率，应采用更保守的复核策略并报告未达目标。

低置信度不等于可靠的范围外检测。已知分类器可能对陌生输入过度自信，因此还需针对非业务文本、多诉求和混合语言专门评估；无法覆盖的未知输入作为系统限制保留。

### 8.1 拟复用 skill 的适配与验证

已阅读 Hugging Face 官方 skills 仓库中的 `huggingface-datasets` 说明，候选版本为 `25910b3d0ba31a2ba102f901cdc9e008c278a69c`。[7] 它描述通过 Dataset Viewer API 查询 split、预览和分页读取数据的方法，适合数据准备时检查镜像结构；skill 本身不是意图分类模型，也不直接执行生产工单分流。

输入为数据集标识、config、split、offset 和 length；输出为结构化元数据或行记录。公开数据只读访问通常不需令牌，私有或受限数据可能需要授权。本项目只使用公开数据的只读子集，不采用说明中的上传数据或上传会话记录能力，不要求读取本机聊天历史。

拟实现适配包括固定允许的数据源、校验参数、限制单页不超过100条、设置超时和最多两次重试、记录分页是否完整，以及将镜像结构与原始 GitHub 数据对照。镜像版本无法固定或内容不一致时，回退到固定提交的原始数据，以原始数据作为最终实验依据。

行为核验覆盖正常 split、错误数据集、分页边界、空结果、超时和响应缺少字段等情况。对比“直接下载原始数据”与“增加 skill 指导的结构核验”两条准备流程，记录能否发现缺页或字段错误及准备耗时；不得将数据准备检查带来的作用冒充模型精度提升。本阶段仅完成说明阅读和适配设计，集成、故障注入及效果核验属于开发阶段工作。

## 9 非功能需求与失败处理

在至少4核 CPU、8 GB内存、无 GPU 的目标机器上运行。验收时记录实际处理器、系统、内存和依赖版本。模型及知识库加载后，单条有效输入在单并发、200次请求测量中的端到端 P95 延迟目标不超过2秒；冷启动另报，不混入稳态延迟。该目标需要实测确认。

原型优先绑定本机地址，不引入多用户认证的额外范围。保存结构化日志，尽量使用工单编号和脱敏文本，避免在异常日志中记录完整账户号、电话号码或邮箱；导出时对可能被表格软件解释为公式的字段作转义。脱敏规则有局限，演示只使用公开或人工构造数据。

| 失败情形 | 规定行为 | 验收观察点 |
| --- | --- | --- |
| 空输入或结构错误 | 阻止处理并说明修正方法 | 不进入模型、不创建正常工单 |
| 低置信度或多意图 | 展示候选并转人工 | 保存触发原因，无静默自动分流 |
| 敏感或高影响诉求 | 强制人工复核 | 不执行真实账户操作 |
| 未找到知识条目 | 标记缺失并转人工 | 不编造业务规定 |
| 模型版本或字段不匹配 | 停止当前推理并提示维护 | 错误可定位，无随机默认标签 |
| 查询超时或数据库失败 | 有限重试后返回失败或待复核 | 无无限循环，无假成功状态 |
| 重复提交 | 基于编号或幂等键识别 | 不创建重复工单 |

用户文本及知识内容都作为数据处理，不能改变系统的权限和流程。包含“忽略规则”等文本时仍按输入策略处理。人工修正可保存为候选训练数据，但不得立即自动回训；需经过脱敏、复核和版本化后进入后续训练。

## 10 评估设计与成功标准

以下数值为初始验收目标，需在开发开始前固定；若未达到，应如实记录、分析并提出改进，不能事后降低门槛后宣称原目标已经达成。

| 维度 | 指标定义 | 初始目标与报告要求 |
| --- | --- | --- |
| 意图识别 | 77类宏平均 F1；每类等权 | 宏平均 F1 ≥ 0.80；同时报告准确率、每类 P/R/F1 和支持数 |
| 自动分流质量 | 正确自动分流数 ÷ 全部自动分流数 | 队列正确率 ≥ 0.95，另报严格意图正确率 |
| 自动分流覆盖 | 自动分流数 ÷ 全部有效域内输入数 | 覆盖率 ≥ 0.50，与正确率联合判断 |
| 复核与拒识 | 应复核样本中被正确拦截的比例 | 边界集复核召回率目标 ≥ 0.90；另报误拦截率 |
| 任务完成 | 最终状态和队列均符合预期的任务数 ÷ 全部任务数 | 60条模拟任务完成率目标 ≥ 0.90；未处理的复核不计完成 |
| 人工效率 | 同等任务条件下完成正确分流的耗时 | 相比纯人工中位耗时下降目标 ≥ 20%；同时报告错误率 |
| 稳定性 | 异常用例是否进入规定的失败或复核状态 | 必测异常用例全部通过，并保存执行证据 |

若自动分流数为0，正确率记为不适用，覆盖率为0，不能宣称达到自动分流要求。准确率与宏平均 F1在全部有效域内测试样本上计算，不因进入人工复核而移除难样本。自动分流质量同时报告分子、分母和95%置信区间，防止小样本造成误导。[6]

人工效率评估拟将60条任务组成难度近似的 A、B 两组，参与者以平衡顺序分别完成纯人工与 Agent 辅助任务，避免同一人重复看到同一文本而产生记忆优势。记录参与人数、经验、有效任务数、错分数和耗时分布。样本较少时只报告探索性结果，不声称普遍节省20%。

对照实验至少包括关键词流程、朴素贝叶斯、最终分类模型直接分流、完整 Agent。消融实验关闭置信度复核或去掉字符特征，分别观察自动分流覆盖率与错分率、模型识别质量的变化；关闭复核的实验只在离线环境执行。选取至少10条具有代表性的失败样例，按相邻意图混淆、歧义、域外输入、规则错误和工具错误分析，改进后用独立样例复验。
